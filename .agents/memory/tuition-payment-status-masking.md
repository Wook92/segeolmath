# 교육비 월별 납부 상태 집계 규칙 (확정)

같은 학생·같은 달에 `tuition_notifications` 행이 2건 이상 존재할 수 있다(안내 재발송 시
취소 없이 새 pending 행이 추가되는 경우 등).

**확정 규칙(사용자 확인):** 그 달의 안내건 중 **하나라도 미결제(pending)면 상태는 "결제대기"**.
즉 우선순위는 `pending > paid > cancelled`. 모든 건이 결제완료일 때만 "결제완료"로 표시한다.
대표 표시 건은 "가장 최근 안내건"을 사용한다.

**Why:** 한 학생에게 한 달에 여러 청구(예: 교육비 + 추가분)가 나갈 수 있고, 일부만 결제한
상태를 "결제완료"로 보이면 미수금이 가려진다. 사용자는 "하나라도 결제 안 됐으면 결제대기"가
맞다고 명확히 확인함. 지난달까지 이 로직(pending 우선)이 정상 동작했음.

**하지 말 것:** 과거에 "paid 우선"으로 바꿨다가(= 하나라도 paid면 결제완료) 되돌린 적 있음.
이는 부분결제/미수금을 가리므로 잘못된 방향이다. 절대 paid 우선으로 집계하지 말 것.

**취소 + 결제대기 동시 노출(사용자 확인):** 대표 상태가 "취소"여도(최근 안내가 취소건)
그 달에 미결제(pending) 안내가 하나라도 남아 있으면 해당 학생은 **결제대기 필터/카운트에도
함께 노출**되어야 한다(취소 카운트에서 빠지는 게 아니라 양쪽 모두). 즉 결제대기 가시성 판정은
`status==="pending" || (status==="cancelled" && 미결제 안내 존재)`.
**Why:** 취소건 뒤에 남은 미수금이 가려지면 안 됨. 사용자가 "결제대기에도 떠야 한다"고 명시 확인.
**How to apply:** 상태별 요약 카드/카운트는 상호 배타가 아니다 — 한 학생이 결제대기와 취소
양쪽에 중복 집계될 수 있음(전체 인원수만 고유). 결제대기 금액 합산 시 취소+pending 학생은
pending 안내건 금액만 더한다.

**참고:** 토스 결제는 클라이언트가 `/payment-result`로 돌아와 confirm을 호출해야만 완료된다.
서버 간 웹훅이 없어, 결제 직후 화면 이동이 끊기면 카드 승인만 되고 시스템엔 pending으로 남을 수
있다. 즉 "결제대기"로 보이는 학생이 실제로 카드 승인은 됐을 가능성도 있으니, 미결제 원인
조사 시 토스 대시보드(외부, Agent 접근 불가)와 대조가 필요할 수 있다.
